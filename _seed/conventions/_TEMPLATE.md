# 规则文件模板

> 复制为 `conventions/<项目名>.md`，填完删掉本行说明。
> **每条规则必须带来源标记和日期**，否则下一个人（或下一次会话的你）不知道它还算不算数。

## 来源标记

| 标记 | 含义 | 怎么来的 |
| --- | --- | --- |
| `[推导]` | 从仓库文件读出来的 | 读 CONTRIBUTING / AGENTS / package.json / 工作流 / 模板 |
| `[观察]` | 从最近 PR 和 issue 里看出来的 | 读最近 20 个已合并 PR、维护者留言、review 行为 |
| `[用户定]` | 只有用户能决定 | 问用户 |

**推导和观察可以自动完成，只有 `[用户定]` 需要问。** 进场时先跑 `references/onboard-project.md` 的采集步骤。

### 3.1 PR 类型接受度

> 决定「这次会话该提哪类 PR」。五类对齐 conventional commits，不要自创分类。
> 默认由 `prtool.py status --author <你>` 的历史统计 + 近 20 个已合并 PR 的类型分布推导。

| 类型 | 本项目态度 | 证据 | 日期 |
| --- | --- | --- | --- |
| `fix` | 欢迎 / 中性 / 谨慎 / 不接受 | 例：近 20 个已合并里 12 个是 fix | `[观察]` |
| `test` | | 例：有纯测试合并，但都补了真实覆盖缺口 | `[观察]` |
| `feat` | | 例：需先在 issue 讨论 | `[推导]` |
| `perf` | | 例：要求附实测数据 | `[推导]` |
| `docs` | | 例：文档 PR 通常当天合 | `[观察]` |

**态度取值**：

| 取值 | 含义 | 对建议的影响 |
| --- | --- | --- |
| **欢迎** | 有多个先例，合并快 | 优先推荐 |
| **中性** | 能合，但要满足条件 | 可以推荐，需说明条件 |
| **谨慎** | 门槛高，需要前置讨论或额外证据 | 不主动推荐，用户要求时才做 |
| **不接受** | 明确拒绝过 | 不推荐，写进 `excluded.md` |
| **未知** | 没有足够样本 | 不要假设，先按通用规则 |

### 3.2 issue 政策

> 决定「什么时候必须先开 issue、什么时候可以直接提 PR」。开错会浪费一轮。

| 项 | 值 | 来源 |
| --- | --- | --- |
| 是否要求先开 issue 再提 PR | 是 / 否 / 视改动大小 | |
| 哪类改动必须先开 issue | 例：新增功能、协议变更、目录结构调整 | `[推导]` CONTRIBUTING / AGENTS |
| 哪类可以直接提 PR | 例：bug 修复、文档、测试 | `[推导]` |
| 是否有 issue 模板 | 路径，或「无」 | `[推导]` |
| issue 标签约定 | 例：`good first issue` 表示欢迎新人 | `[观察]` |
| PR 正文关联 issue 的写法 | `Fixes #N` / `Closes #N` / `Refs #N`，或项目另有约定 | `[推导]` |

**判定原则**（没有项目规则时用）：

| 改动性质 | 直接提 PR | 先开 issue |
| --- | --- | --- |
| 修可复现的 bug，改动 < 200 行 | ✅ | 可选，看维护者习惯 |
| 纯文档 / 测试 / 平台兼容 | ✅ | 不用 |
| 新增功能 | ❌ | 必须先谈 |
| 改协议、状态机、目录结构 | ❌ | 必须先谈 |
| 维护者明确说过「这个我自己改」 | ❌ | 不用开，直接放弃 |
| 不确定 | — | 先开 issue 问一句，成本很低 |
