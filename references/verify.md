# 验证候选

> 触发：手上有一个候选，要判断它值不值得提 PR。
> **这一步决定 PR 会被合并还是被关闭。** 大多数失败不是代码写错，是证据不够。

## 一、三级证据（从弱到强）

| 级别 | 形态 | 能提 PR 吗 |
| --- | --- | --- |
| **L1 注入故障** | 假 IO、假程序、人为 ENOSPC/EPERM | ❌ **默认不能**。多数维护者不认「注入的故障」 |
| **L2 真实运行** | 真机跑出来的错误、真实日志、真实第三方 API 返回 | ✅ 可以，但要能稳定复现 |
| **L3 文档/平台依据** | 仓库自己文档的矛盾、上游平台硬限制、仓库自身既有约定 | ✅ 最强，最难被驳 |

**L2 与 L3 结合最有说服力**：既证明了真实会发生，又绑到对方无法否认的依据上（平台硬限制、官方文档、仓库自己的注释）。

> ⚠️ 每个项目的实际门槛不同，**查 `conventions/<项目>.md` 的「维护者政策 · 新增兜底分支的证据门槛」**。该字段为空时按 L2/L3 执行。

## 二、兜底类修复的额外门槛

提交前先问：**「这条路径现在会丢数据/误合并，还是只是慢和说法不准？」**

- 丢数据 / 误合并 → 可以提
- 只是慢、只是日志说法不准 → **先不开 PR**，记进 `excluded.md` 等真机证据

> 若 `conventions` 里写了更严的门槛（例如「必须有真实事故记录」），以项目规则为准。

## 三、变异验证（证明测试真的守护）

「现在就能过」的测试必须证明它能守住行为，否则就是复述实现。

**步骤**：

1. `git diff --stat` 记下当前改动范围（恢复时要能一眼看出有没有多改）
2. 改坏对应分支（删掉它、或改成错误行为）
3. 跑测试，确认**只有对应用例变红**
4. **用 `git checkout -- <实现文件>` 恢复**；该文件还有别的未提交改动时，先 `git stash push -- <实现文件>`，恢复后再 `git stash pop`
5. `git diff --stat` 确认只剩原来的改动，再跑一次确认全绿

```powershell
git diff --stat
# 改坏：正则替换。写回用 UTF8 无 BOM；不要用 Set-Content / Out-File，它们会按平台换行重写整个文件
$p = Resolve-Path <实现文件>
$text = Get-Content $p -Raw
[IO.File]::WriteAllText($p, ($text -replace '<对应分支的正则>', ''), (New-Object Text.UTF8Encoding($false)))
<该项目的测试命令，见 conventions>
# 恢复：不要靠备份副本，直接回到 git 里的版本
git checkout -- <实现文件>
git diff --stat
```

**判据**：

- 改坏后测试仍然全绿 → 这条用例没有守护价值，要重写。
- **`(?m)$` 在 Windows 上可能匹配不到行尾**：文件是 CRLF 时行尾是 `\r`，正则要写 `\r?$`，或按行处理。用 `git ls-files --eol <文件>` 先看一眼换行。
- **同一处修复有多段独立逻辑时，逐段单独变异**：两段各自能红，PR 的 Verified 段才能写清「哪条用例守住哪一半」。

## 四、先红后绿（修 bug 类）

修 bug 的 PR 必须有「修改前变红、修改后变绿」的实测记录，写进 PR 正文。

- 新测试写好后，先在**未修改的代码**上跑一次，记下失败输出
- 再应用修复，跑一次，记下通过
- 两个数字/输出都写进 PR 正文

> 维护者常会自己复跑确认，所以数字必须真实。

## 五、对抗验证

把候选交给一个**只看代码、不看结论**的独立视角，回答三句：

1. 改的这个函数还有谁在用？
2. 接外部程序的，有没有真实运行记录？
3. 同类问题别处还有没有？

**结论只取三态**：

- `confirmed`：有最小复现和影响
- `needs_validation`：缺哪个事实，不给严重度
- `rejected`：被哪一层挡住了

**严重度只给 confirmed**。「另一层挡住了」只算加固建议，不算 bug。

## 六、严重度门槛

默认口径如下。**项目有自己的分级时，以 `conventions/<项目>.md` 的「严重度口径」为准。**

| 级别 | 判据 | 通道 |
| --- | --- | --- |
| S1 安全 | 无密钥能进门、来源冒名、身份越界、事件能决定执行目标/目录/权限、数据外泄 | **私密 Security Advisory**，不开公开 issue/PR |
| S1 正确性 | 误合并/误上线、跳过必需检查、丢一轮、重复派、回执错导致业务重做 | 公开 issue + PR（`Fixes #N`） |
| S2 高 | 用户可见的错误结果但可恢复 | 正常 PR |
| S3 中 | 静默行为偏差、错误提示缺失 | 正常 PR |
| S4 低 | 纯测试/文档/文案/本机环境 | 视用户偏好（见 `preferences.md`） |

## 七、常见驳回理由（提前自查）

| 驳回理由 | 怎么避免 |
| --- | --- |
| 「注入的故障不算」 | 用 L2/L3 证据 |
| 「另一层挡住了」 | 先确认没有兜底层 |
| 「这是契约不是缺陷」 | 先读测试，看有没有用例明确固化了这个行为 |
| 「这是产品决策」 | 先开 issue 谈方向 |
| 「CI 已覆盖」 | 本机能跑的不算盲区 |
| 「我自己改」 | 同类问题不再提第二次 |
| 「这不符合本项目的方向」 | 先读 `conventions` 的「明确拒绝过的方向」 |

## 八、证明「没有守护」——负向断言怎么算成立

「有测试守护」是正向断言，一条命中就能成立。「没有守护」是负向断言，必须**穷举**才成立——而它恰恰最容易翻车：判错了会直接变成一个「测试已经存在」的空 PR，烧的是你在维护者那里的信用。

**三条硬要求**：

1. **按文件名定位，整段读。** 判定某个不变量或函数有没有测试，先找 `tests/` 下对应模块的 `<模块>.test.ts`，从头读到尾。很多项目的测试文件在开头用注释逐条列出它覆盖的失败场景——那就是现成的覆盖清单。
2. **检索结果被截断时，不许下结论。** `grep` / `Select-String` 只取了前 N 条、或工具提示输出被截断，都只能算「我看到的这部分里没有」。要么去掉条数限制取全量，要么换更窄的检索（直接搜断言原文、搜用例标题）。
3. **在 `coverage.md` 里留痕。** 每条「无守护 / 只验单侧」必须写清读过哪些测试文件、用过什么检索命令。字段见 `_seed/projects/_template/coverage.md`；`scripts/prtool.py check` 会拦住没有引用 `tests/` 文件的缺口行。

**判定顺序**（不要跳步）：

| 步 | 做什么 | 结论 |
| --- | --- | --- |
| 1 | 找到对应模块的测试文件，整段读 | 文件不存在 → 这才可能是「无守护」 |
| 2 | 文件里搜该行为的关键词（断言原文、用例名） | 命中 → 有守护，结束 |
| 3 | 全量检索整个 `tests/`，不加任何条数限制 | 命中 → 有守护，结束 |
| 4 | 前三步都空，才写「无守护」，并记录第 1、3 步的文件与命令 | 缺口成立 |

**记法**：`有守护` 要给出 `文件:行号`；`无守护` 要给出「读过哪些文件 + 检索了什么」。只有后一种能引出测试 PR，所以它必须比前一种更严格。

> 真实案例（2026-11-27，agent-autoloop）：搜卡片页转义时只看了检索命中的前 15 条，就判「HTML 转义零守护」，正准备开测试 PR；实际 `tests/http.test.ts:321` 早就把 `<script>alert(1)</script>` 当卡片标题验过转义。同理把「跨轮 run token」判成缺守护，而 `tests/runs.test.ts:516` 的用例名就是「a run token works only for its run」。**在一个有 104 个测试文件的项目上，我差点提交一个「测试已经存在」的 PR。**

## 九、跨后端移植查询：只借形状，不借语义

> 触发：把兄弟 provider / 兄弟模块的查询写法搬过来（ES 的 `terms` → Couchbase 的 query、SQL 方言之间、正则引擎之间、ORM 之间）。

**同一个「形状」在不同后端是不同语义。** 兄弟 provider 里 `{"terms": {"metadata.document_id.keyword": ids}}` 能用，不等于目标后端的 `TermQuery(field="metadata.document_id")` 能用——前者打在 keyword 子字段上、不分析；后者可能打在 standard analyzer 建出来的 text 字段上，而 `term` 查询偏偏不分析输入。

**三个必答**（写进候选证据，不能口头过）：

| # | 必答 | 证据从哪来 |
| --- | --- | --- |
| 1 | 目标后端里这个字段**怎么建的**？analyzer 是什么、有没有 keyword 子字段、是不是 dynamic 映射出来的？ | 索引定义的 JSON / 建表 DDL / ORM 模型；不是猜 |
| 2 | 这种查询类型**会分析输入吗**？ | ES / Couchbase：`term` 不分析，`match` / `match_phrase` 按字段 analyzer 分析；SQL 看 collation |
| 3 | 值里**有没有分隔符**？连字符 UUID、路径、邮箱、大小写混排被拆 token 后，整串 term 会不会 0 命中？反过来，analyzed 查询会不会命中别的文档（`or` 操作符就是）？ | 拿真实 id 代入第 1、2 步推一遍 |

**证据只认索引映射 + 官方文档，mock 不算。** mock 只能证明「你传了什么形状」，不能证明「后端怎么解释它」。真集群跑不了时，PR 正文必须写成「单测证明请求形状；语义未验证，等 e2e」——写成「已验证」就是过度声明。

**测试约定（机械可查的那一半）**：跨后端过滤 / 查询的用例必须用**真实格式的 id**（连字符 UUID、带分隔符的键、带大小写的编码），不能用 `d-1` / `a` / `doc-1` 这类单一 token 的假值——单一 token 在 analyzer 面前是恒真的，拆不拆 token 都命中，等于没测。至少要有「真实格式 id → 命中」和「另一个真实格式 id → 不命中」两条。

**写进证据的位置**：`candidates.md` 的「待提」档，跨后端查询类候选的证据摘要必须含三行——① 字段怎么建的（analyzer / keyword / dynamic）② 查询是否分析 ③ 值里的分隔符拆 token 后会不会 0 命中。缺一行不许升到待提。

> 真实案例（2026-11-27，dify vdb-couchbase #47401）：照 ES 家族的 `term` 形状写了 `TermQuery`，但 Couchbase 索引 `default_analyzer: standard` + `metadata.dynamic: true`，连字符 UUID 被拆成 5 个 token，整串 term 在真集群 0 命中；mock 断言全绿。dosubot 指出后改成 analyzed 的 `match` + `and` 算子。**那份索引 JSON 就在同一个文件里，读过却没和「term 不分析」连起来。**

## 十、不许夸大：四种量词与四种真实翻车

> 规则本体在 `SKILL.md` 硬规则 15。这一节只放**怎么判断自己正在夸大**。

### 四个高危量词，每个都要下一句给得出处

| 量词 | 必须给什么 |
| --- | --- |
| **最多 / 至少** | 触发条件 + 实测数字。「上限」不等于「常态」 |
| **唯一 / 全部** | 穷举方式。见第八节：负向断言要穷举 |
| **必然 / 一定** | 反例检查。找不到反例 ≠ 不存在反例 |
| **罕见 / 常见** | 频次数据。没有频次就写「未测频次」 |

其余诸如「工作量很大」「依据最硬」「成本高」「期望值高」，也都算估价，同样要有出处或标「未测」。

### 四种真实翻车（2026-11-27 / 28，agent-autoloop）

| 我说过的 | 实际 | 错在哪 |
| --- | --- | --- |
| 「`cli/wakeups.ts` 逐条 `why()`，**最多 100 轮串行**」 | `cli/wakeups.ts:19-23` 只在事件 ≥20 条、或含 `timer.due` / `card.answered` 时才发 `why()`，普通历史一次都不发 | 把**上限**当成**常态**，据此提了一个实测只值 1.5 倍的 perf 候选 |
| 「INV-09 要造上一版的版本化 fixture，**工作量大**，是唯一整块空白」 | 仓库有 35 个 release tag，`git show <tag>:<路径>` 就是现成 fixture；半小时扫完 | 把**没查过**写成了**成本高**，结果这条被挂了一整天 |
| 「B（PR 模板语言）**最便宜、依据最硬**」 | 依据只有「语言不一致」，而「不一致算不算问题」由维护者定义 | 把**偏好**当成了**依据** |
| 「中文模板让我**受害**」 | 模板只是诱因；用中文是我读完模板后的决定，而且我还回头把 `conventions` 里对的规则改错了 | 把**自己的选择**写成**被外部加害** |

**共同点**：四次都不是数据错，是**给数据加的形容词**超出了数据能承载的范围。用户为此浪费的时间，全部花在「先信了估价、再去验证、发现不成立」这个循环上。

### 自检：一句话

写完一句话之后问自己：**「这个数字/判断，我是量的，还是想的？」**

- 量的 → 把量法一起写（工具、样本、环境），数字才有说服力
- 想的 → 就地改成「未测」，然后决定要不要花时间量。**超过半小时的估价尤其要标「未测」**，因为它会直接影响用户对下一步的取舍

## 十一、本机把测试跑起来（依赖装不上时）

CI 的命令原样抄到本机经常跑不通：没有 `make`、平台相关的依赖编译失败、锁文件解析被 `exclude-newer` 过滤、大 wheel 超时。固定动作：

1. 优先用仓库自带的 `uv run` / `api/.venv`；**别在项目 venv 里反复重装**
2. 跑不通再建独立环境：`python -m venv .venv-<用途>`（放仓库外或 gitignore 里）
3. 按 `pyproject` 的 `[project].dependencies` 装，不走 lockfile；慢就换镜像源
4. 跑测试时把仓库根目录挂进 `PYTHONPATH`（`PYTHONPATH=<repo>`）
5. 把**实际跑通的那条命令原文**记进 `conventions` §2 的「本机等价命令」，下次直接抄

`uv sync` / `pip install` 失败不等于项目坏了：先看真实错误（常见是 `exclude-newer` 过滤掉 build 依赖、或 wheel 超时），再决定是覆盖过滤参数还是绕过。**不要为了跑测试去改项目的依赖声明。**
