# 验证候选

> 触发：手上有一个候选，要判断它值不值得提 PR。
> **这一步决定 PR 会被合并还是被关闭。** 大多数失败不是代码写错，是证据不够。

## 一、三级证据（从弱到强）

| 级别 | 形态 | 能提 PR 吗 |
| --- | --- | --- |
| **L1 注入故障** | 假 IO、假程序、人为 ENOSPC/EPERM | ❌ **默认不能**。多数维护者不认「注入的故障」 |
| **L2 真实运行** | 真机跑出来的错误、真实日志、真实第三方 API 返回 | ✅ 可以，但要能稳定复现 |
| **L3 文档/平台依据** | 仓库自己文档的矛盾、上游平台硬限制、仓库自身既有约定 | ✅ 最强，最难被驳 |

**L2 与 L3 结合最有说服力**：既证明了真实会发生，又绑到对方无法否认的依据上（平台硬限制、官方文档、仓库自己的注释）。

> ⚠️ 每个项目的实际门槛不同，**查 `conventions/<项目>.md` 的「维护者政策 · 新增兜底分支的证据门槛」**。该字段为空时按 L2/L3 执行。

## 二、兜底类修复的额外门槛

提交前先问：**「这条路径现在会丢数据/误合并，还是只是慢和说法不准？」**

- 丢数据 / 误合并 → 可以提
- 只是慢、只是日志说法不准 → **先不开 PR**，记进 `excluded.md` 等真机证据

> 若 `conventions` 里写了更严的门槛（例如「必须有真实事故记录」），以项目规则为准。

## 三、变异验证（证明测试真的守护）

「现在就能过」的测试必须证明它能守住行为，否则就是复述实现。

**步骤**：

1. 备份实现文件
2. 改坏对应分支（删掉它、或改成错误行为）
3. 跑测试，确认**只有对应用例变红**
4. 恢复实现，确认全绿

```powershell
# 1. 备份
Copy-Item <实现文件> tmp\orig.bak -Force
# 2. 改坏（删掉某个分支，或改成错误行为）
$text = Get-Content <实现文件> -Raw
$mutated = $text -replace '<对应分支的正则>', ''
[IO.File]::WriteAllText((Join-Path (Get-Location) '<实现文件>'), $mutated, (New-Object Text.UTF8Encoding($false)))
# 3. 跑，看哪条红
<该项目的测试命令，见 conventions>
# 4. 恢复
Copy-Item tmp\orig.bak <实现文件> -Force
```

**判定标准**：如果改坏后测试仍然全绿，那这条用例没有守护价值，要重写。

## 四、先红后绿（修 bug 类）

修 bug 的 PR 必须有「修改前变红、修改后变绿」的实测记录，写进 PR 正文。

- 新测试写好后，先在**未修改的代码**上跑一次，记下失败输出
- 再应用修复，跑一次，记下通过
- 两个数字/输出都写进 PR 正文

> 维护者常会自己复跑确认，所以数字必须真实。

## 五、对抗验证

把候选交给一个**只看代码、不看结论**的独立视角，回答三句：

1. 改的这个函数还有谁在用？
2. 接外部程序的，有没有真实运行记录？
3. 同类问题别处还有没有？

**结论只取三态**：

- `confirmed`：有最小复现和影响
- `needs_validation`：缺哪个事实，不给严重度
- `rejected`：被哪一层挡住了

**严重度只给 confirmed**。「另一层挡住了」只算加固建议，不算 bug。

## 六、严重度门槛

默认口径如下。**项目有自己的分级时，以 `conventions/<项目>.md` 的「严重度口径」为准。**

| 级别 | 判据 | 通道 |
| --- | --- | --- |
| S1 安全 | 无密钥能进门、来源冒名、身份越界、事件能决定执行目标/目录/权限、数据外泄 | **私密 Security Advisory**，不开公开 issue/PR |
| S1 正确性 | 误合并/误上线、跳过必需检查、丢一轮、重复派、回执错导致业务重做 | 公开 issue + PR（`Fixes #N`） |
| S2 高 | 用户可见的错误结果但可恢复 | 正常 PR |
| S3 中 | 静默行为偏差、错误提示缺失 | 正常 PR |
| S4 低 | 纯测试/文档/文案/本机环境 | 视用户偏好（见 `preferences.md`） |

## 七、常见驳回理由（提前自查）

| 驳回理由 | 怎么避免 |
| --- | --- |
| 「注入的故障不算」 | 用 L2/L3 证据 |
| 「另一层挡住了」 | 先确认没有兜底层 |
| 「这是契约不是缺陷」 | 先读测试，看有没有用例明确固化了这个行为 |
| 「这是产品决策」 | 先开 issue 谈方向 |
| 「CI 已覆盖」 | 本机能跑的不算盲区 |
| 「我自己改」 | 同类问题不再提第二次 |
| 「这不符合本项目的方向」 | 先读 `conventions` 的「明确拒绝过的方向」 |

## 八、证明「没有守护」——负向断言怎么算成立

「有测试守护」是正向断言，一条命中就能成立。「没有守护」是负向断言，必须**穷举**才成立——而它恰恰最容易翻车：判错了会直接变成一个「测试已经存在」的空 PR，烧的是你在维护者那里的信用。

**三条硬要求**：

1. **按文件名定位，整段读。** 判定某个不变量或函数有没有测试，先找 `tests/` 下对应模块的 `<模块>.test.ts`，从头读到尾。很多项目的测试文件在开头用注释逐条列出它覆盖的失败场景——那就是现成的覆盖清单。
2. **检索结果被截断时，不许下结论。** `grep` / `Select-String` 只取了前 N 条、或工具提示输出被截断，都只能算「我看到的这部分里没有」。要么去掉条数限制取全量，要么换更窄的检索（直接搜断言原文、搜用例标题）。
3. **在 `coverage.md` 里留痕。** 每条「无守护 / 只验单侧」必须写清读过哪些测试文件、用过什么检索命令。字段见 `_seed/projects/_template/coverage.md`；`scripts/prtool.py check` 会拦住没有引用 `tests/` 文件的缺口行。

**判定顺序**（不要跳步）：

| 步 | 做什么 | 结论 |
| --- | --- | --- |
| 1 | 找到对应模块的测试文件，整段读 | 文件不存在 → 这才可能是「无守护」 |
| 2 | 文件里搜该行为的关键词（断言原文、用例名） | 命中 → 有守护，结束 |
| 3 | 全量检索整个 `tests/`，不加任何条数限制 | 命中 → 有守护，结束 |
| 4 | 前三步都空，才写「无守护」，并记录第 1、3 步的文件与命令 | 缺口成立 |

**记法**：`有守护` 要给出 `文件:行号`；`无守护` 要给出「读过哪些文件 + 检索了什么」。只有后一种能引出测试 PR，所以它必须比前一种更严格。

> 真实案例（2026-11-27，agent-autoloop）：搜卡片页转义时只看了检索命中的前 15 条，就判「HTML 转义零守护」，正准备开测试 PR；实际 `tests/http.test.ts:321` 早就把 `<script>alert(1)</script>` 当卡片标题验过转义。同理把「跨轮 run token」判成缺守护，而 `tests/runs.test.ts:516` 的用例名就是「a run token works only for its run」。**在一个有 104 个测试文件的项目上，我差点提交一个「测试已经存在」的 PR。**
