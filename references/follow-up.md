# 跟进与止损

> 触发：PR 有结果了（合并/关闭/review 意见），或要判断某个项目该不该继续。
> **时限和止损线查 `preferences.md`；没有该文件时用本文的默认值。**

## 一、维护者回复后要做什么

**先判断他是哪种 review 风格**（`conventions/<项目>.md` 的「维护者政策 · review 风格」写明了）：

| 风格 | 迹象 | 你该做什么 |
| --- | --- | --- |
| 写 line review | 有 review 评论挂在代码行上 | 逐条回复 + 改 |
| 只在 issue 里留言 | 没有 line review，但 PR 讨论区有长留言 | 读完整段，按留言改 |
| 直接改你的分支 | 没有评论，但 commit 变了 | **读他改了什么**，理解为什么 |
| 静默合并 | 什么都没发生就 merged | 自己 diff 一遍，看有没有被改 |

**编辑型维护者（直接改分支）必做**：

```powershell
git fetch fork; git log --oneline origin/main..fork/<你的分支>
git diff <你的最后一个 commit>..fork/<你的分支>
```

读他补的内容——**这是下次最该学的东西**。

## 二、维护者补的边角怎么记

**每次都要写进 `ledger.md`**，因为它告诉你下次该把哪些边角写全。

记录格式：**他补了什么 → 说明他关心什么 → 下次怎么写**。

常见类型：

| 补的类型 | 说明他关心什么 |
| --- | --- |
| 补同类漏项 | 你要一次搜完，别只修撞到的那一处 |
| 补其他平台/身份的对称性 | 别只顾自己用的场景 |
| 收紧语义边界 | 改规则时要界定边界，不能一律放宽 |
| 补文档/注释 | 行为改了要同步文档 |
| 纠正你的表述 | 注释和 PR 正文里的类比也要验证 |

## 三、PR 结果的处理

| 结果 | 动作 |
| --- | --- |
| **合并** | 记 `state/prs.jsonl`（status=merged, merged_at）；`ledger.md` 补维护者改了什么；`_index.md` 更新 |
| **合并但改了很多** | 同上，并在 `profile.md` 的维护者画像里补一条 |
| **关闭未合并** | 记 status=closed；`ledger.md` 写清驳回理由；`excluded.md` 加一条防重复；判断是否需要调整策略 |
| **长期无回应** | 超过 `preferences.md` 的止损天数 → 在 `_index.md` 标「已止损」 |

## 四、止损规则

**默认触发条件**（任一，可在 `preferences.md` 覆盖）：

- 连续 2 个 PR 14 天无 review
- 外部 PR 合并停摆超过 2 周
- 维护者明确表示某个方向他自己改，且同类问题再提一次仍被忽略

**动作**：

1. `_index.md` 状态改为「已止损」
2. 写明原因和日期
3. **不删除记录**，避免下次会话重复尝试
4. 回到 `choose-project.md` 重新选项目

## 五、什么时候该继续加注

- 维护者连续 2 次以上在你的分支上补边角后合并 → 信任已建立，可以推 S2
- 维护者主动在 issue 里 @你 或问你的意见 → 强信号，可以谈设计
- 你的 PR 被写进发布说明 → 说明价值被认可

## 六、在审到上限时（同一项目 3 条）

同一项目同时最多 3 条 open PR（硬规则 13）。到顶之后：

- **不再挖新候选、不提新 PR**——这一轮的全部工作就是跟进
- 按 `preferences.md` 的响应时限（默认 24 小时）盯 review；有意见当天改，不要拖到「攒一批一起改」
- 维护者要求改的地方改完就回复一句，不要静默更新
- 有名额空出来（合并或关闭）才回到 `hunt-candidate.md`
- 破例只有用户明确要求，并且要在 `candidates.md` 记一行理由

**零 review 也要有产出**（都不产生新 PR）：

1. 给已有候选补证据：L2 / L3 的复现、日志、真实包，写进 `candidates.md` 的「待验证」档（只验证，不动代码）
2. 把 PR 里写着「未验证，等 e2e」的部分查清楚；查不了就在 PR 里补一句说明，别让它一直挂着
3. 更新 `conventions` 里过期的 `[观察]`（首响中位、合并节奏这类 90 天就该重测的）
4. 读维护者最近合并的 PR，把「他关心什么」写进 `profile.md`
5. 给下一条候选写红测试，**可以写、可以跑，但不开分支、不提交**

## 七、CI 变红了怎么办

1. **先确认红的 run 属于哪个 head**：`gh pr view <n> --json headRefOid` 与失败 run 的 `headSha` 比对。旧 head 的红 run 是历史——按新 head 重跑过就翻篇，**不要照着旧日志改代码**
2. 自己分支 + 零 review + 失败原因是 lint / 格式 → `git commit --amend` + `git push --force-with-lease`，保持单提交
3. 已经有人 review（哪怕只是 dosubot 之外的维护者留言）→ **追加 commit，不 force**，别重写他的 review 上下文
4. 外部原因（依赖拉取失败、flaky、runner 挂）→ 先重跑一次再判断，**不要为了变绿改代码**
5. 失败原因是 hook / formatter 改写了文件 → 把 hook 的 diff 抄进 `ledger.md`，并在 `conventions` §2 补一条本机可执行的等价检查
6. 修完在 PR 里留一句「fixed the lint failure from the previous head」，免得后面翻 Actions 列表时误读

**fork PR 的绿色是假象**：`action_required` 的 suite 没有 check run，`statusCheckRollup` 会显示 SUCCESS。用 `prtool.py mine --repo <repo>` 看「N 待批」，别把「没有红」当成「跑过了」。

## 八、不要做的事

- ❌ 在 issue 里催 PR
- ❌ 维护者说「我自己改」后，同类问题再提第二次
- ❌ 同一个项目同时开两个严重 PR
- ❌ 同一项目在审已有 3 条时还提新 PR（到顶只跟进）
- ❌ 维护者合并后立刻开下一个，不看他改了什么
- ❌ 反复提交同一类批量补丁（会显得在刷数量）
