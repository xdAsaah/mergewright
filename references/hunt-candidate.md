# 单项目内找候选

> 触发：在已选定的项目里挖「下一个能提的 PR」。
> 前提：先读该项目的 `excluded.md`，**不要重走已排除的方向**。

## 一、六种扫描手法（按性价比排序）

### 1. 导出函数 × 测试覆盖反查

找出「导出了但测试里从未出现名字」的函数——零覆盖往往意味着某条分支没人守。

```powershell
# 收集所有导出名，与测试全文比对（路径按项目改）
$exports = @{}
Get-ChildItem <源码目录> -Filter *.ts -Recurse | ForEach-Object {
  Select-String -Path $_.FullName -Pattern '^export (async )?function (\w+)|^export const (\w+)' -AllMatches |
    ForEach-Object { foreach ($m in $_.Matches) { $n = if ($m.Groups[2].Value) { $m.Groups[2].Value } else { $m.Groups[3].Value }; if ($n) { $exports[$n] = $_.Path } } }
}
$tests = (Get-ChildItem <测试目录> -Recurse -Include *.test.ts,*.spec.ts | ForEach-Object { Get-Content $_.FullName -Raw }) -join "`n"
$exports.Keys | Where-Object { $tests -notmatch [regex]::Escape($_) } | Sort-Object
```

Python / Go / Rust 同理：换成 `^def |^func [A-Z]|^pub fn` 之类的导出模式。

**注意**：零覆盖 ≠ 该测。先判断这个函数的行为是否已被**间接**覆盖（通过上层调用），再决定。

⚠️ **别拿被截断的检索结果当证据。** `Select-String ... | Select-Object -First 15` 这类写法会静默丢命中，只看到前几条就断言「没有测试」是这个技能最容易犯、代价最大的错——它会变成一个「测试已经存在」的空 PR。判定「没有守护」的完整方法见 `references/verify.md` 第八节：按文件名定位、整段读测试文件、检索取全量。

### 2. 文档承诺 × 测试反查

`docs/`、`README`、`SECURITY.md` 里每一条「会做 X」「不会做 Y」都是承诺。逐条问「有测试守它吗」。

> 案例：某个项目在文档里承诺「`.ps1` 走 PowerShell、`.bat` 拒绝、`.cmd` 只在命名出可运行入口时接」，三条全无测试——补上就是一条纯测试 PR。

### 3. 截断点扫描

```powershell
Select-String -Path <源码目录>\*.<ext> -Pattern '\.slice\(0,\s*\w+\)|substring\(0,|padEnd\(|\.slice\(-' 
```

按码点切分是安全的；按字节切会切开多字节字符（UTF-16 代理对、UTF-8 多字节）。这类 bug 通常维护者已修过很多次，**重点看新代码**。

### 4. 同族漏项扫描

找到一处「A 处做了 X 防护，B 处没做」后，**全库搜一遍同类**，别只修撞到的那一处。

> 案例（匿名）：某个项目里修「子进程不弹控制台窗口」，只找到一处漏项就提了 PR，维护者合并时补了另外两处。**同一类漏项要一次搜完，否则显得没做功课。**

### 5. 平台差异扫描

维护者通常只在自己的开发平台上跑。你换个平台就可能撞到：

| 平台 | 常见盲区 |
| --- | --- |
| Windows | 子进程隐藏窗口、路径分隔符与引号、`.cmd`/`.ps1` shim、控制台代码页、文件锁、符号链接权限、ACL |
| macOS | `launchctl`、app bundle 路径、`~` 展开、Gatekeeper |
| Linux | `DISPLAY`/`WAYLAND_DISPLAY`、`notify-send`、权限位 |

**这类是维护者盲区，即使产品行为零变化也值得提**（但一个项目最多一条，见 `preferences.md`）。

### 6. 状态组合矩阵

把「入口 × 身份 × 状态」列成表，逐格问「换个人来、换个状态，还能不能做」。入口和身份按项目改。

| | 管理员 | 执行者 | 通道 | 数据源 | 公开链接 |
| --- | --- | --- | --- | --- | --- |
| 排队中 | | | | | |
| 执行中 | | | | | |
| 状态未知 | | | | | |
| 待决事项 | | | | | |
| 已决事项 | | | | | |
| 凭证过期 | | | | | |

### 7. issue 扫描

**这是最容易被忽略、也最容易合并的候选来源。** 维护者自己开出来的 issue，说明他确认了这是个问题。

```bash
python scripts/prtool.py issues --repo owner/repo
```

输出会按优先级排序，并自动标记：

| 标记 | 含义 | 该怎么用 |
| --- | --- | --- |
| **新手友好** | 有 `good first issue` / `beginner` / `easy` 标签 | 优先看，维护者明确表示适合新人 |
| **欢迎 PR** | 有 `help wanted` / `pr welcome` 标签 | 优先看，维护者明确表示接受外部 PR |
| **长期未修** | ≥90 天且未认领 | 看有没有人讨论过、为什么没修 |
| **已认领** | 有 assignee | **不要碰**，别人在做 |
| **已有 PR 在审** | 有 open 状态的关联 PR | **不要碰**，会撞车 |
| **已修待确认** | 有已合并的关联 PR，但 issue 还开着 | 大概率已修好，只是忘了关。先去验证，不要重做 |
| **有相关 PR** | 有关联 PR，但已关闭未合并 | 看关闭理由——如果是因为方案不对，换个思路可能还能做 |
| **多 PR 未合×N** | ≥3 个已关闭未合并的关联 PR | **PR 坟场**：先问维护者，别急着做。见下 |

关联 PR 通过 timeline / cross-reference 查询，默认只查前 15 个（`--linked-limit`），每个多一次请求。不想查用 `--no-linked`。「多 PR 未合」的阈值用 `--min-failed-prs` 调，默认 3。

**「已有 PR 在审」和「已修待确认」是省时间的关键标记**——没有它，你可能会花半天做出一个已经有人做完的修复。

### PR 坟场怎么处理

一个 issue 上挂着 5 个、10 个被关闭的 PR，说明**不是没人做，而是做的都没通过**。原因通常有三类：

| 原因 | 怎么判断 | 该怎么做 |
| --- | --- | --- |
| 方案没谈拢 | 每个 PR 被拒理由都不同，维护者一直在提新要求 | 先在 issue 里问清「到底要什么」，谈拢再做 |
| 问题本身难 | PR 都做了但测试不过、或引入新 bug | 读完所有失败 PR 的评论，找出共同卡点 |
| 维护者不想改 | 被拒理由一致是「won't fix」「by design」 | 放弃，写进 `excluded.md` |

**不要因为「有 10 个 PR 失败」就直接跳过。** 反过来说，这类 issue 的价值往往最高：需求被反复确认过，只是没人做对。如果你能看出前 10 次为什么失败，第 11 次就成了。

**动手前必做**：把失败 PR 的评论读一遍，尤其看维护者在里面重复说了什么。重复出现的要求就是真正的验收标准。

**还要看的两类**（工具不标，要自己读）：

- **维护者在评论里说「PR welcome」**——没打标签但态度明确
- **反复被 +1 的老 issue**——说明真实需求，优先级高

**判定一个 issue 能不能做成 PR**：

1. 有没有人已经在做？看 `issues` 输出的「已有 PR 在审」标记、assignee、最近评论
2. 讨论是否收敛？如果还在争论方案，先别动，这是设计型改动
3. 能不能小步解决？大 issue 只做其中一小块，不要试图一次解决全部
4. 维护者的最后一条评论是什么时候？如果是半年前且没人理，可能是他改变主意了
5. **有关联 PR 但被关闭的**，一定要读关闭理由——被拒的是「这个方案」还是「这个问题」

**记录**：看过的 issue 写进 `projects/<项目>/issues.md`，避免下次重看。

## 二、每个候选必须回答四个问题

1. **谁会碰到？** 真实用户场景，还是只有测试能触发？
2. **后果是什么？** 丢数据/误操作/误合并（严重），还是慢/文案不准（轻）？
3. **证据是什么？** 见 `verify.md` 的三级证据。
4. **有没有别的层挡住了？** 挡住了只算加固建议，不算 bug。

## 三、记录

每扫完一轮，往 `state/scans.jsonl` 追加一条：

```json
{"ts":"2026-11-27T02:00:00Z","project":"<项目>","scope":"<扫了什么>","head":"<提交号>","verdict":"none","severity":null,"evidence":"<结论与依据>","next":"<下一步>"}
```

`verdict` 取值：`confirmed` / `needs_validation` / `rejected` / `none`。

候选本身写进 `projects/<项目>/candidates.md` 的「待验证」档，**筛掉的移到 `excluded.md`**，不要删。
