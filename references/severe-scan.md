# 严重 bug 扫描（S1/S2 线）

> 触发：项目信任已建立（≥1 merged），要找高价值 bug。
> **排查可以并行开始，但 PR 必须排队**——同一时间只允许一个严重 PR 在审。

## 一、先建本项目的不变量清单

**不变量是项目专有的，不要照搬别的项目。** 放在 `conventions/<项目>.md` 的第 5 节。

怎么写：

1. 读该项目的 `docs/`、`SECURITY.md`、核心模块注释，找出「系统承诺不会发生的事」
2. 每条写成**可断言的句子**（能翻译成测试断言）
3. 覆盖这几类（按项目性质取舍）：

| 类别 | 典型不变量 |
| --- | --- |
| 鉴权 | 无凭证 / 错种类凭证进不了门；身份不能冒用；令牌不能跨作用域 |
| 输入隔离 | 用户输入不进入执行路径（提示词、命令、路径、权限） |
| 幂等 | 同一输入不产生两次副作用；重放安全 |
| 不丢 | 已接受的工作不静默丢失；失败要可恢复 |
| 不越权 | 只操作授权范围；不执行未审查的代码 |
| 可审计 | 关键动作留痕；记录不能被伪造 |
| 兼容 | 老配置/老插件不改也能跑 |

**没有不变量清单就不做严重线**——否则会退化成随机翻代码。

## 二、覆盖缺口清单怎么做

1. 对 INV-01…10 逐条找到守护它的测试
2. 每条产出三列：**不变量 / 守护测试 / 缺口**
3. 缺口分三类：**无守护**、**只有 happy path**、**只验单侧**
4. 「有守护」的判定标准是**改坏实现它会红**（见 `verify.md` 的变异验证）——恒真的断言不算
5. 清单写在 `projects/<项目>/coverage.md`，**不进上游仓库**。从 `_seed/projects/_template/coverage.md` 建。
6. **「无守护」这种负向判定必须按 `references/verify.md` 第八节走**：按文件名定位、整段读测试文件、检索取全量，并在清单里留下读过哪些文件、用过什么命令。`prtool.py check` 会拦住没有引用 `tests/` 文件的缺口行。判错的代价是一个「测试已经存在」的空 PR。

## 三、攻击面矩阵

把项目的**入口 × 身份 × 状态**列成表，逐格问「换个人来、换个状态，还能不能做」。

以 HTTP 服务类项目为例（其他类型按自己的入口替换）：

| | 管理员 | 执行者 | 通道 | 数据源 | 公开链接 |
| --- | --- | --- | --- | --- | --- |
| 排队中 | | | | | |
| 执行中 | | | | | |
| 状态未知 | | | | | |
| 待决事项 | | | | | |
| 已决事项 | | | | | |
| 凭证过期 | | | | | |

**怎么找入口**：读路由表 / 命令表 / 消息处理器，把每个能改变状态的入口列出来。优先看「持链接即授权」「回调」「重放」这三类。

## 四、精准故障注入（不做随机乱打）

部分失败类 bug 依赖**精确的故障点和时机**，随机注入命中率很低。可用手法（按项目类型取舍）：

- 假外部 API：5xx、半截响应、超时、部分成功（标签只清一半、状态只写一半）
- 假 CLI：非零退出但错误 JSON 在 stdout、权限不足、重复事件
- 进程信号：SIGKILL / 崩溃恢复、并发写
- 平台特例：本机能跑但 CI 不能跑的环境差异（**这是维护者盲区，价值最高**）

⚠️ **注入复现只算线索，不算事故**（见 `verify.md` 的三级证据与项目门槛）。

## 五、预算与止损

- 一次会话只推进一条线的一次完整扫描
- 空手而归就把方向记入 `excluded.md`，下次不重复
- 连续 2 轮没有 S1/S2 结论 → 暂停严重线，回到 issue 相邻的 S3 修复
- 一个严重 PR 在审时，不开第二个严重 PR

## 六、每轮扫描的记录格式

```json
{"ts":"...","project":"<项目>","scope":"<扫了什么>","head":"<提交号>","verdict":"none","severity":null,"evidence":"<结论与依据>","next":"<下一步>"}
```

## 七、安全类走私密通道

S1 安全类必须走**私密安全报告通道**（GitHub Security Advisory / 项目 SECURITY.md 指定的方式），不开公开 issue/PR。报告里同时给补丁方案，公开 PR 等维护者披露后再提。
