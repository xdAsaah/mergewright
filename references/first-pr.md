# 首 PR 与阶段策略

> 触发：首次进入一个项目、或决定下一枪该打什么。

## 一、阶段划分

| 阶段 | 目标 | 允许做什么 |
| --- | --- | --- |
| **信任建立**（0–1 个 merged） | 证明「按规范交付 + 可复现 + 响应快」 | 低价值 PR 是敲门砖：文档勘误、平台兼容、测试基础设施 |
| **低严重度积累**（1–3 个 merged） | 建立稳定预期 | D1–D2 的真实行为修复，优先用户可感知的 |
| **严重线**（≥3 个 merged） | 争取核心模块 | S2/S1，一次只开一个严重 PR |

## 二、被合并 PR 的特征

> 下面这些是**常见形态，不是硬性门槛**。你的项目如果数据不同，以实际观察为准——把观察写进 `conventions/<项目>.md` 的「维护者政策」，别套用通用数字。

1. **标题即验收标准**：「场景 + 旧行为 → 新行为」，写不出来说明边界没想清。
2. **修状态，不加功能**：新功能 PR 的合并门槛通常远高于修 bug。
3. **小而完整**：单点修复通常几十到两百行、几个文件。跨十几个文件的大改动基本都会被打回。
4. **带回归测试**：能变红的那种，不是复述实现。
5. **合并是双通道**：单点修复快（小时级），跨模块慢（天级，且常撞批量合并窗口）。
6. **作者信用累积**：头部作者的 PR 更容易被快速处理，前几枪决定后续待遇。
7. **与维护者活动区错位**：避开他正在重构的文件。

## 三、被拒绝的 5 类反模式

1. **注入故障复现的兜底**——没有真实事故记录。
2. **设计型大改**——issue 里没讨论过就提。
3. **顺手重构**——修 bug 顺带整理周围代码。
4. **纯样式/格式**——除非维护者明确要求。
5. **产品决策类**——需要他拍板的方向，先开 issue 谈。

## 四、信任建立后不再提低价值 PR

**低价值** = 产品行为零变化（纯测试/文档/注释/依赖整理）、维护者明说会自己改的、用户不可感知的、只修本机环境问题的。

**例外只有三条**：
1. 维护者的盲区——他做不到而你能做到（Windows 实机、真实第三方授权链路、非提权账户场景）
2. 是后续高价值 PR 的前置
3. 维护者在 issue/PR 里明确要求

**自检问句**：「如果这条 PR 是别人提的，我觉得它值得写进发布说明吗？」答否即为低价值。

**低价值 PR 提不提，查 `preferences.md`。** 默认策略：信任建立前可以提（敲门砖），信任建立后原则上停做，只保留三个例外（盲区 / 前置 / 维护者要求）。

## 五、PR 节奏

- 一个 PR 解决一个问题。
- 同一时间只允许一个严重 PR 在审。
- 排查可以并行开始（不占 review 带宽），但 PR 必须排队。
- 维护者 review 回来后 24 小时内响应。
