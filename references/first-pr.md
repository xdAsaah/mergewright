# 首 PR 与阶段策略

> 触发：首次进入一个项目、或决定下一枪该打什么。

## 一、阶段划分

| 阶段 | 目标 | 允许做什么 |
| --- | --- | --- |
| **信任建立**（0–1 个 merged） | 证明「按规范交付 + 可复现 + 响应快」 | 低价值 PR 是敲门砖：文档勘误、平台兼容、测试基础设施 |
| **低严重度积累**（1–3 个 merged） | 建立稳定预期 | D1–D2 的真实行为修复，优先用户可感知的 |
| **严重线**（≥3 个 merged） | 争取核心模块 | S2/S1，一次只开一个严重 PR |

## 二、被合并 PR 的特征

> 下面这些是**常见形态，不是硬性门槛**。你的项目如果数据不同，以实际观察为准——把观察写进 `conventions/<项目>.md` 的「维护者政策」，别套用通用数字。

1. **标题即验收标准**：「场景 + 旧行为 → 新行为」，写不出来说明边界没想清。
2. **修状态，不加功能**：新功能 PR 的合并门槛通常远高于修 bug。
3. **小而完整**：单点修复通常几十到两百行、几个文件。跨十几个文件的大改动基本都会被打回。
4. **带回归测试**：能变红的那种，不是复述实现。
5. **合并是双通道**：单点修复快（小时级），跨模块慢（天级，且常撞批量合并窗口）。
6. **作者信用累积**：头部作者的 PR 更容易被快速处理，前几枪决定后续待遇。
7. **与维护者活动区错位**：避开他正在重构的文件。

## 三、被拒绝的 5 类反模式

1. **注入故障复现的兜底**——没有真实事故记录。
2. **设计型大改**——issue 里没讨论过就提。
3. **顺手重构**——修 bug 顺带整理周围代码。
4. **纯样式/格式**——除非维护者明确要求。
5. **产品决策类**——需要他拍板的方向，先开 issue 谈。

## 四、信任建立后不再提低价值 PR

**低价值** = 产品行为零变化（纯测试/文档/注释/依赖整理）、维护者明说会自己改的、用户不可感知的、只修本机环境问题的。

**例外只有三条**：
1. 维护者的盲区——他做不到而你能做到（Windows 实机、真实第三方授权链路、非提权账户场景）
2. 是后续高价值 PR 的前置
3. 维护者在 issue/PR 里明确要求

**自检问句**：「如果这条 PR 是别人提的，我觉得它值得写进发布说明吗？」答否即为低价值。

**低价值 PR 提不提，查 `preferences.md`。** 默认策略：信任建立前可以提（敲门砖），信任建立后原则上停做，只保留三个例外（盲区 / 前置 / 维护者要求）。

## 五、PR 节奏

- 一个 PR 解决一个问题。
- 同一时间只允许一个严重 PR 在审。
- 排查可以并行开始（不占 review 带宽），但 PR 必须排队。
- 维护者 review 回来后 24 小时内响应。

## 六、每次会话都要定类型

> **这条适用于每一次会话，不只是第一个 PR。** 阶段只决定「建议什么」，不决定「不问」。

### 类型只有五类

`fix` / `test` / `feat` / `perf` / `docs`，对齐 conventional commits，不要自创分类。

### 三个输入

| 输入 | 从哪读 | 作用 |
| --- | --- | --- |
| **阶段** | 数该项目 `ledger.md` 里 merged 的个数 | 0–1 信任建立；1–3 低严重度；≥3 可上严重线 |
| **项目接受度** | `conventions/<项目>.md` 的「PR 类型接受度」表 | 欢迎/中性/谨慎/不接受 |
| **自己的历史** | `prtool.py status --repo <repo> --author <你>` 的「按类型」段 | 哪类在这个项目里合并率高 |

### 怎么给建议

1. 先按阶段过滤：信任建立期 → 优先 docs/test/fix（D1）；低严重度期 → fix 为主；严重线 → 允许 S2/S1
2. 再按项目接受度过滤：标「不接受」的直接排除；标「谨慎」的不主动推荐
3. 最后按自己的历史排序：同类合并率高的优先

**三者冲突时以「项目接受度」为准**——那是这个仓库的客观事实，你的历史样本可能太小。

### 怎么问用户

**必须问，不能替用户决定。** 格式：

```
这个项目当前阶段：<阶段>（已合并 N 个）
按项目接受度和你的历史，建议这次做 <类型>，因为 <一句话依据>。

你想做哪类？
  A. fix   —— <这个项目里的合并率 / 有没有合适候选>
  B. test  —— ...
  C. docs  —— ...
  D. 其他（feat / perf），或者你已经有具体目标
```

**注意**：

- 不要列全部五类，只列有候选或推荐的
- 每类附一句「为什么推荐/不推荐」
- 用户选了「不接受」的类型时，提醒一次风险，但**不要阻止**——最终由用户决定

### 挖完之后

候选池里每条必须带类型（见 `projects/_template/candidates.md`）。挖完一轮填「类型分布」表，看是不是全挤在一个类型里。

如果用户选的是 `docs` 或 `test`，而项目接受度是「谨慎」，挖到候选后要额外说明「这类在这个项目里门槛高，要不要换个类型」。

## 七、类型效果要回填

每 5 个 PR 更新一次 `ledger.md` 的「类型复盘」表：

| 类型 | 提交 | 合并 | 关闭 | 合并率 |
| --- | --- | --- | --- | --- |

数字从 `status` 现算，不要手写。这张表决定下次建议什么——如果 `test` 类合并率 100%，就该多提；如果 `feat` 全是关闭，就该停。
